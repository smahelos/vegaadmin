# Application

Use cases called by delivery (controllers, Livewire, Artisan commands). Allowed dependencies: `architecture.md`. Shape of a use case: `references/layers.md`.

- A use case is a pair of classes in its context: `Commands/CreateContact.php` + `Commands/CreateContactHandler.php`, or the same under `Queries/`. A **Command** changes data, a **Query** only reads. Both terms come from CQRS: "command" always means this use case, and a console class is always called an "Artisan command". Helpers that handlers share live in `Support/`, without `Service` in the name.
- The declaration is a `final readonly class` implementing `CommandInterface` or `QueryInterface` (`App\Application\Shared\UseCase\Contracts`). It holds its typed input as public properties (ids as value objects, the record's owner as `UserId`, data as `<Entity>WriteData`), declares its access in the required static `access(): Access` (`permissions.md`) and states its result as the interface's type: `@implements CommandInterface<ContactDTO>`, or `<null>` when there is none. A use case over one owner's data extends the abstract `App\Application\Shared\UseCase\OwnedUseCase`, which holds the owner as `public UserId $owner`.
- The handler is a `final` class with one public method, `handle(CreateContact $command, WriteScope $scope)` (`ReadScope` for a Query, `AllOwnersScope` for a use case over every owner's data, no scope for any other use case without `OwnedUseCase`), returning a DTO, a `<Operation>Result` or nothing. The gate calls it by name, so a rule in `phpstan/Rules/` checks that the declared result exists and matches `handle`.
- **A use case runs only through the gate, which checks permission and owner** (`permissions.md`); a handler repeats neither. A handler reads records through the scope (a Command passes `$scope->read` to a read port) and throws the context's not-found exception when one is missing: the same answer for "does not exist" and "belongs to someone else". Entity limits run in the handler, inside the transaction (`permissions.md`). A form page has its own Query; there is no separate `authorize…` method.
- The gate opens one transaction around every Command; a repository never opens one, and Queries run without one. A Command that calls outside the database (payment gateway, bank, e-mail, PDF, files) implements `CallsOutsideDatabaseInterface`: the gate opens no transaction and the handler opens it through `TransactionBoundaryInterface` only around its writes. A Command running in a transaction never runs a Command with this interface. The domain events a use case publishes reach their handlers, listeners and queued jobs in step with the transaction (`architecture.md`, Events).
- Reading data that has no owner and answers the same for anyone, anonymous included (published pages, countries, currencies, the public company register), is a plain `final` read class outside the gate. It reaches no owner's data, because that needs a scope. A read that calls an external service is rate limited in delivery, per user or per IP for an anonymous visitor (`config/billex.php`).
- Input validation of request data belongs to form requests (`http.md`); business validation belongs to Domain value objects and services. Application holds no third copy of either.
- Presentation formatting (money, dates, labels for one screen) lives in `Presenters/`, using `MoneyFormatterInterface` and the translation port.
